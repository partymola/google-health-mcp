# Auth, tokens, failure classification and retries

Part of the agent guide: [AGENTS.md](../../AGENTS.md) says when to read this file.

- **Auth**: `auth.py` - Google OAuth setup and token refresh. Access tokens last an hour; refresh tokens do not rotate, which is what lets a token minted on a machine with a browser be copied to a headless one. Scopes come from `GOOGLE_SCOPE_READERS` in `config.py`, which names what is read under each one and from which `GOOGLE_SCOPES` is built; after widening them, re-run `google-health-mcp auth`. Where the list comes from and why is stated once, beside the constant. `test_no_scope_is_asked_for_that_nothing_reads` asserts the readers are *equal* to what the sync fetches, in both directions: a scope with no reader is a permission the user grants for nothing, and a scope deleted while something still fetches its types is a 403 that reads like a publishing problem. **A grant never gains scopes on refresh, so a release that adds one leaves every install short until the person consents again, and the shortfall is reported on every surface.** The token file keeps the `scope` string Google reports on consent and refresh. Absent means unknown, not none, and blank counts as absent, so `run_sync` forces a refresh that replaces it. A scope holding nothing requested gets the same refresh before anything is skipped, because junk there would otherwise skip every type with no request left to correct it. That costs one request per sync on a grant that really is empty, and the types stay skipped if the refresh reports nothing requested: `TestAScopeThatReadsAsHoldingNothing`. A stored `expires_at` that is missing, not a finite number or far in the past refreshes on the next call, which replaces it, so `doctor` grades it OK and does not ask for `auth`: `test_a_stored_expiry_that_is_not_finite_is_refreshed` and `test_an_expiry_the_next_refresh_replaces_does_not_advise_auth`. `doctor` says "valid until" only for a token the next call would send, reading the same `config.ACCESS_TOKEN_REFRESH_BUFFER` as `_usable`: `test_doctor_agrees_with_what_the_next_call_does`. A stored `refresh_token_expires_at` that is not a number is dropped: `test_a_stored_granted_expiry_that_is_not_a_number_is_replaced`. Stored tokens are held to `is_token`: an access token failing it is refreshed, and a refresh token failing it is a refusal with no request: `test_a_stored_access_token_that_is_not_a_token_is_refreshed_rather_than_sent` and `test_a_stored_refresh_token_that_is_not_a_token_is_not_sent`. **`doctor` grades FAIL only on the refresh token**, since the next call repairs a bad access token with one request and `auth` would rewrite a file this host may not own: `test_a_bad_access_token_beside_a_good_refresh_token_is_not_a_failure` and `test_a_token_the_server_will_not_use_is_not_reported_as_present`. With no usable refresh token it says the next call is refused rather than refreshed: `test_a_token_the_next_call_cannot_refresh_is_not_said_to_be`. `is_token` and `is_number` live in `config` because `doctor` may not import `auth`. Each sync records the requested scopes the grant lacks, by name only, in the `authorisation` table, and leaves the record alone when the token says nothing, so a token caught mid-rewrite cannot erase a known shortfall. `require_auth` adds an `authorisation` note to every object response from that record, which is what lets a cache-only host with no token carry it. `doctor` reports it under `missing-scopes`, preferring the token where it records scopes, except in offline mode, where the token is not the host's to read. `sync` prints it to stderr. **A type read under a scope the grant lacks is skipped, not failed**: `HANDLER_SCOPES` in `google_sync.py` names the scopes each handler reads under, and `run_sync` logs such a type `skipped`, which neither the CLI's exit code nor `doctor`'s sync-log check treats as failure. Otherwise every upgrade that adds a scope would turn every hourly sync red until the person consented again. A scope trimmed out of `GOOGLE_SCOPE_READERS` counts as not granted, and unknown counts as held. A token from before scopes were recorded is unknown until its next refresh, so `run_sync` forces one (`refresh_google_token(force=True)`) when the token records none; otherwise the first sync after an upgrade would fetch what the grant lacks and fail. `account` gates its three records one by one in `_ACCOUNT_RECORDS`, since they sit under three scopes. `TestEachHandlerIsGatedOnTheScopesItReads` in `tests/test_config.py` holds each entry equal to the scopes of the readers its handler calls; the rest is pinned across `tests/test_authorisation.py`. **Consenting as an account not linked to Google Health** produces a grant that authorises but reads nothing: Google answers every request with 400 `FAILED_PRECONDITION`, reason `ACCOUNT_NOT_LINKED`, which `google_get` raises as `AccountNotLinked`, an auth error naming the fix. `auth` makes one request after saving the tokens (`_finish_consent`) and fails with the same message. Any other failure of that request says nothing about the account and is ignored, including a 403 from a grant without the settings scope. Pinned by `TestFinishingAConsent` in `tests/test_google_auth.py`. `_save_json`'s `hasattr(os, "fchmod")` asks whether the call exists, not whether this is POSIX, and since 3.13 it exists on Windows too - where it is not a no-op but sets the read-only attribute from the owner-write bit, so at 0o600 it clears it. Nothing there restricts the file to one account on Windows; do not read the guard as meaning the call is skipped there. **The callback listener is `_CallbackServer`, not a bare `HTTPServer`, and that matters on Windows.** `HTTPServer` sets `allow_reuse_address`, which on POSIX only waives TIME_WAIT. On Windows it is consent to be displaced: per Microsoft's same-user table for a specific-address bind, a first socket holding the address with `SO_REUSEADDR` is bound over by a second one asking for the same, so another process could take the authorisation code - which is enough to obtain the tokens. **Not asking is what closes it** - the same table shows a first bind with neither option refusing that second bind. `SO_EXCLUSIVEADDRUSE` is asked for as well because Microsoft recommends it for server sockets and because it is the half that would still hold for a wildcard bind, which this listener is not. Never ask for both: reuse requested after exclusive use is the configuration Microsoft calls insecure, and `allow_reuse_port` (the POSIX-side equivalent hazard) is pinned off for the same reason. The cost is Windows-only - the port stays held until the previous connection has finished closing, normally a couple of minutes, and `auth` has to be retried until it has - which is also why `setup_google_auth` catches the resulting `OSError` and binds before opening the browser rather than after. `doctor`'s port probe asks for reuse on POSIX only, for the matching reason; the two must stay in step. `TestTheCallbackPortIsNotShared` in `tests/test_auth.py` drives the Windows branch on a POSIX runner against a recording socket rather than reading the source for it - source assertions here let the option be set after the bind, at the wrong level, on the wrong socket, or with a value of 0, all of which pass a check that only looks for the name
- **The credential files are the only copy of the tokens.** `_refresh_google_token` reads the token file on every call, and the client file whenever it refreshes, under `_google_token_lock`, and keeps nothing between calls, because `google-health-mcp auth` replaces them from another process while the server runs. Held in memory, the old grant stays in use until a restart: after a Testing-mode expiry that means sending a dead refresh token, and the first refresh after a re-consent saves the old refresh token and scopes back over the new ones. The lock is held across the refresh request, so a slow one holds every token request in the process for up to its timeout. After a successful refresh the token file is read again, and **a file that changed during the request is never saved over**: its token is used if it is still valid, and otherwise the refreshed token is returned unsaved and the next call refreshes from the file. A refused refresh reads it again too, since the refusal judged a refresh token `auth` may already have replaced: a changed file's valid token is used, and any other change is a `RefreshNetworkError` rather than a refusal. **"Changed" is deliberately inequality, not a later `expires_at`**: an expiry written on another host carries that host's clock, so a consent from a host running behind can look older than a token still valid here, which is exactly what a forced refresh starts from. Leaving a refresh unsaved costs only an access token, because Google's refresh tokens do not rotate; do not port this rule to a provider whose tokens do. For the same reason a 200 with no usable access token is raised with nothing saved, even if it carries a `refresh_token`: the stored one is still good. The price of the rule is deliberate: an older copy of the file written during the request, by a restore or a file-sync conflict, wins over the refresh, and if its refresh token is dead the next call is refused. Pinned by `TestTheTokenFileIsTheOnlyCopy` in `tests/test_google_auth.py`; its rewrites keep the file's length and mtime, so a cache keyed on either fails it. A refresh answer's `refresh_token` replaces the stored one only if `is_token` accepts it, RFC 6749's token syntax and not only spaces, and anything else counts as omitted, since saving it would lose the only copy: `test_an_unusable_refresh_token_keeps_the_stored_one`. `is_token` does not close printable junk: it checks syntax, so a `refresh_token` that is well-formed and wrong still replaces the stored one, and the next refresh sends it. **What this does not close**, the first three across processes, which the lock does not reach: `_save_json` truncates and then writes, so the first read in a call can land inside another process's write and is reported as a refusal, against the classification rule below, and every request reads the file, so this window is open on each one; two writers at once can interleave and corrupt the file; a write landing between the second read and the save is overwritten; and, in any process, a save that fails or is killed after the truncate leaves an empty file, which only `auth` repairs, since there is no other copy. A write to a temporary file followed by `os.replace` would close the first, second and last on POSIX, and is not done. Nor is a huge finite lifetime closed: `1e300`, or an expiry in milliseconds, still never refreshes, because `is_number` refuses only what is not a finite number a float can hold, and a cap would be an invented number.
- **Failure classification**: `refresh_google_token` is a boundary over `_refresh_google_token` and raises exactly two types. `TokenRefused` only where the server or the credential files judged the credentials unusable; `RefreshNetworkError` for everything else, via a catch-all, so an unanticipated failure lands there by construction rather than by listing exception types. `google_get` maps the first to `HealthAuthError`, which `doctor` grades FAIL and answers with "run auth" - rotating the token file the syncing host owns - and the second to `HealthNetworkError`, a `HealthAPIError`, which grades WARN. `google_get` raises the same class for a request that got no answer (any `OSError` or `http.client.HTTPException`), so it covers no answer, or a token refresh answered 200 with no token, and the route sync depends on that classification to tell an outage from one workout's failure. (In offline mode `doctor` grades both WARN: a token cannot be checked without the network.) **Never widen `TokenRefused` to a condition that can clear on its own** (a rate limit, a 403 from a WAF, an unreadable response, a 200 carrying no usable token). Pinned by `TestTheGoogleRefreshBoundary` in `tests/test_google_auth.py`, and at the client by `TestTheTokenLayerIsClassified` and `TestAgainstTheRealGoogleRefresh` in `tests/test_google_api.py`. Note: nothing in the sync layer sleeps on a 429 - a rate limit surfaces as a `rate_limited` status for that type and the next run resumes from the cursor. **`google_get` does sleep on a 500, 502 or 503.** It sends the request again after each of `SERVER_ERROR_WAITS`. If the last attempt fails too, it raises the same `API error <code>` one attempt would have. A one-off server error therefore does not fail the type. A lasting one does, except on a route export, which is left out as described under `exercise_routes` in [schema.md](schema.md). Each retry is a round trip as well as a wait. A lasting outage therefore makes a full sync minutes slower to fail. A `Retry-After` on a 5xx is not read, since only these bounded waits may run on a tool call's thread. **500 is retried deliberately, against AIP-194**, which says to surface INTERNAL at once. The 500s measured on a real sync cleared by the next run, and one that never clears costs only the bounded delay per request. Each retry is logged at INFO with the status and the operation, the only record that one happened. Nothing else is retried there. A 504 is retried with a halved page only while listing data points. A 429 reports its wait, and a request with no answer raises `HealthNetworkError` at once. The token refresh runs before the loop, so a 5xx from the token endpoint is not retried either. Pinned by `TestAServerErrorIsRetried` in `tests/test_google_api.py`
