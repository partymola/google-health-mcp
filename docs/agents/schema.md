# Database schema

Part of the agent guide: [AGENTS.md](../../AGENTS.md) says when to read this file.

SQLite at `~/.local/share/google-health-mcp/google_health.db` (gitignored). The exact column definitions live in `SCHEMA` in `src/google_health_mcp/db.py` (the source of truth); the list below is a navigational overview that also notes the non-obvious semantics.

- `heart_rate` - date, resting_hr, zones (JSON), calculation_method, data_source (JSON)
- `heart_rate_zones` - date, zone_boundaries (the day's four zones as Google sent them, decoded on read). **`daily-heart-rate-zones` is read from `reconcile`, not `list`.** Measured: where Google holds two zone records for a day, a `list` request whose window includes that day answers every date in the window twice with differing zones, and which copy matches a single-day request varies by date. `reconcile` answers each date once and matched the single-day answer on every date checked. It carries no `dataSource`, so the table has none. Pinned by `test_a_day_is_its_zones_read_from_the_merged_stream`. A date one answer still carries twice keeps the later point, as every daily type does: `test_a_date_answered_twice_keeps_the_later_point`
- `activity` - date, steps, calories_out, active_minutes, very/fairly/lightly active, sedentary, floors, distance_km. **The five minute columns have no source in this API and arrive only by import**, so on an install with no imported history they stay NULL - and `health_trends activity` reports `avg_active_minutes` from one of them, which is `null` in every period until something fills it. Reasoning for not deriving them: `sync_activity`'s docstring. **`calories_out` is declared INTEGER and holds Google's value with its decimals**, as do `food_log.calories_in` and `exercises.calories`: SQLite keeps a REAL in an INTEGER column whenever converting it would lose information, so a synced 2508.9 reads back as 2508.9. Do not cast them back to whole numbers; pinned by `test_four_rollups_land_in_one_row`, `test_energy_and_water_land_in_one_row` and `test_calories_are_kept_as_sent`
- `exercises` - log_id, date, name, duration_min, calories, avg_hr, steps, distance_km, distance_unit, start_time, source, log_type, and from Google also end_time, the two UTC offsets, active_seconds (Google's own duration, beside the rounded minutes), notes, create/update time, and as JSON decoded on read (`db._JSON_COLUMNS`) metrics_summary, exercise_metadata, exercise_events, splits, split_summaries and data_source. The sync names every one of these on every write, absent ones as `None`, so a revised workout withdraws what Google stopped sending; an imported row never names them. A workout deleted in the app is removed with its route by the sweep in [sync.md](sync.md), and an imported one is never touched (`test_a_deleted_workout_and_its_route_leave_the_cache`). `health_get_exercises` returns the three arrays only with `include_detail`, and otherwise how many each holds, `null` where none is stored as `health_get_ecg` reports an absent trace (`TestTheToolKeepsTheLongArraysBehindAFlag`, `test_a_workout_with_nothing_stored_counts_null_rather_than_nought`). `null` covers every case of nothing stored, which the column cannot tell apart: an imported workout, Google sent none (`_json` stores an empty array as NULL), the workout was synced before these columns existed, or the stored text will not decode (`db._decoded`). `health_get_sleep_sessions` counts a missing array as 0 instead, because there the record is the whole point as sent
- `sleep` - date, total_minutes, efficiency, start/end_time, deep/light/rem/wake_minutes, sessions (one row per night; a fragmented night's sessions are summed, `sessions` > 1 flags the split), sleep_period_minutes
- `weight` - date, weight_kg, bmi, fat_pct, google_columns (the columns Google wrote, as a JSON list; `db.query_weight` leaves it out of what tools return). A day whose weigh-ins or body-fat readings were all deleted has that figure withdrawn, and only a figure Google wrote; an imported `bmi` keeps the row (`test_a_day_keeps_an_imported_bmi_beside_a_withdrawn_weight`)
- `spo2` - date, avg, min, max, avg_ci_low, avg_ci_high, std_dev (Google's standard deviation of the daily averages over the past 7 to 30 days, not of the night's samples), data_source
- `hrv` - date, daily_rmssd, deep_rmssd, entropy, non_rem_hr, data_source
- `azm` - date, total_minutes, fat_burn_minutes, cardio_minutes, peak_minutes
- `breathing_rate` - date, breaths_per_min, data_source
- `skin_temperature` - date, nightly_relative (degrees C from baseline), log_type, nightly_absolute, baseline, nightly_stddev_30d, data_source
- `core_temperature` - datetime (YYYY-MM-DDThh:mm:ss), date, temp_celsius, reading_id (Google's `id`), measurement_location (the enum as sent), data_source; PRIMARY KEY (datetime, temp_celsius) - manually-logged body temp keyed by timestamp+value so multiple (even same-second) readings per day are preserved while an exact repeat corrects the row. **An edit in the app keeps the reading's `id` and changes its value** (measured 21 Nov 2026 on a value edit), which lands under a new key, so the old key is a reading Google no longer sends and the sweep in [sync.md](sync.md) removes it, as it does a deleted reading. Keyed on time and value, the sweep keeps every key the answer holds, whatever id each carries, so the mirror case below loses nothing. Pinned by `test_an_edited_value_replaces_the_earlier_one`, `test_an_edited_time_replaces_the_earlier_one`, `test_a_reading_deleted_in_the_app_is_removed`, `test_a_save_that_fails_removes_nothing`, `test_a_row_outside_the_window_is_never_removed`, `test_an_id_sent_under_two_keys_in_one_answer_keeps_both`, `test_a_reading_the_sync_cannot_read_is_no_evidence` and `test_a_reading_this_sync_did_not_write_is_never_removed`. Keying on `reading_id` instead would need a table rebuild, which `MIGRATIONS` cannot express. An edit to a reading older than the incremental overlap is reached only by `--since` or `live`. The mirror case: two distinct readings in the same second with the same value are one row, and the last one's id and location win
- `cardio_fitness` - date, vo2_max_low, vo2_max_high (a reported range), vo2_max (a single value), and beside the single value Google's cardio_fitness_level, estimated (1 or 0) and vo2_max_covariance, and data_source
- `food_log` - date, calories_in, water_ml, from Google's daily rollups; each entry behind them is in `food_entries` and `water_entries`. A day a rollup no longer answers for has that column withdrawn, and a day left with neither is removed (`test_a_days_totals_follow_what_google_still_holds`)
- `ecg` - reading_id, date, start_time, avg_bpm, classification, lead_number, sampling_hz, scaling_factor, duration_sec, waveform, device_model. `classification` is stored as the enum given (`NORMAL_SINUS_RHYTHM`, `ATRIAL_FIBRILLATION`, four inconclusive variants, unspecified, not-analyzed) rather than collapsed to a boolean. `waveform` is the sample array as JSON text and `duration_sec` is stored rather than derived on read, because the interval carries only a start time - a reading's length is samples over frequency, and without a frequency there is no duration
- `irn` - alert_id, date, start_time, end_time, alert_windows (JSON text), device_model
- `account` - resource (`profile`, `settings`, `irn_profile`), body (the JSON Google returned, whole), fetched_at (UTC). Records of the account rather than dated series, so the sync window does not apply and each run replaces the record; an empty or non-object answer writes nothing. A record that fails is re-raised after the others are stored, so the type still fails; no answer, a token refresh answered 200 with no token, or a rate limit stops at once. **This is deliberately the opposite of `exercise_routes`**: an account has three fixed records and one that keeps failing is worth seeing, while routes are one per workout and one bad workout must not fail the rest
- `height` - datetime, date, height_mm (millimetres, as Google reports it). Every sync reads the whole history rather than its window, because the usual case is one reading logged years before any incremental window
- `exercise_routes` - log_id (the exercise's resource name), date, tcx (the export text as Google sent it, stored compressed). Only exercises whose `hasGps` is `true` are exported, and a route already held is not fetched again. Days `_days_another_provider_recorded` leaves to an import are skipped here too, since the workout listed for such a day carries the import's id and a route stored under Google's could not be looked up. One workout whose export fails (an error status, a 504, an unreadable answer, an empty export, a name the export refuses) is left out and logged, and reaches neither the result nor `sync_log`, so it cannot fail the type on every run. A later sync asks again only while the workout is inside its window; past the incremental overlap it needs `--since`, and nothing reports that it is missing. `HealthNetworkError` (no answer, or a token refresh answered 200 with no token), a refusal or a rate limit fails the type, since the next export would share it. An export answered with 500, 502 or 503 is retried before it is left out. So while the export endpoint keeps failing, every GPS workout the sync still has to fetch costs the full retry delay. `GoogleGatewayTimeout` is a `HealthAPIError` so that a 504 outside the paging loop is an API error rather than one `run_sync` calls unexpected. `health_get_exercise_route` returns the text only when asked, as `health_get_ecg` does the waveform
- `sleep_sessions` - session_id (the session's resource name), date (its local end, the same rule the nightly `sleep` row follows, so the two agree on a night), start_time, end_time, record (the point exactly as Google sent it, `dataSource` included, stored compressed). One row per session where `sleep` sums a night; nothing in the record is computed. `health_get_sleep_sessions` returns the three segment arrays only with `include_stages`, and otherwise how many each holds (`test_the_segments_stay_behind_their_flag`). A count is 0 when the record lacks the array, since the record is the whole point and Google sent none
- `weight_readings`, `body_fat_readings` - reading_id (the point's resource name), datetime and date (the sample's own civil time, as the daily `weight` row uses), record (the point as Google sent it, in Google's own unit). Every reading where `weight` keeps one a day, and neither table writes the other. Each handler makes its own literal fetch and passes the points to `_store_readings`, because the scope check reads the data type off the handler's own body. A reading deleted in the app is removed by the sweep in [sync.md](sync.md). Both are in doctor's `_USER_LOGGED_TYPES` with `weight`
- `sedentary_periods`, `altitude_gains`, `swim_lengths` - date (the civil date each point's interval starts on, which is what the list filter reads), points (that day's points exactly as Google answered them, stored compressed). **One row a local day rather than one a point**: the points carry no `name`, and Google's data-management guide says an interval can change after it is first sent, so no per-point key survives a re-derivation, and a stale row would then sit beside its replacement. `_store_day_lists` writes them and each handler makes its own literal fetch, as the reading tables do. **Each request carries a day of margin either side (`_with_margin`) and only the days asked for are stored**, so no stored day sits at the edge of a request, where a merged stream could answer it in part: `test_the_request_has_a_day_of_margin_and_only_the_range_is_stored`. Sedentary periods are read from `reconcile`, since phone tracking can write them too; its points carry no `dataSource` (measured). Altitude and swim lengths are read from `list`, keeping `dataSource`; where measured, each had one source. The points are stored as sent, so their integers stay strings: every day-list table is the exception to converting every numeric field. `health_get_activity_events` serves all three, 7 days by default, each event as its interval and values unless `include_records` is set. Doctor leaves altitude and swim lengths unjudged (`_UNJUDGED_DEVICE_TYPES`): altitude is recorded only on days with a climb, and passive swim detection can end with nothing broken. Pinned in `tests/test_activity_events.py`, by `test_a_resync_replaces_the_days_list` and `test_a_day_the_answer_lacks_keeps_what_it_had` among others
- `respiratory_rate_sleep` - a day-list table like the three above, dated by each summary's civil sample time. **Every summary's `name` has an empty data-point id**, so all of them share one name and a key on it would hold one row for the whole history (`test_summaries_sharing_one_name_are_all_kept`). A night can carry several, all inside one sleep session; whether those are later versions or separate segments is not known. Read from `list`, which answered the same points as `reconcile`, keeping `dataSource`. `health_get_breathing_rate` returns them only with `include_sleep_summaries`
- `food_entries`, `water_entries` - date (the civil date each entry's interval starts on), points (that day's `nutrition-log` or `hydration-log` points as sent, stored compressed). **Each entry carries a distinct `name`, and they are still kept a day at a time on purpose**: a re-sync replaces a day's entries whole, as sent, as every day-list table does, so an edited or deleted entry needs no bookkeeping of its own. Two entries were measured sharing a start minute, so a key on time would merge them: `test_the_day_holds_every_entry_as_sent`. On entries logged in the app, `endTime` falls seconds after `startTime`, a back-dated entry included (measured), so it says nothing about when the entry was saved. Read from `list`, keeping `dataSource`; on the account measured it answered the same as `reconcile`, from one source. **A day whose every entry was deleted is absent from `list`, `reconcile` and the daily rollup alike** (measured), so the sweep in [sync.md](sync.md) removes it here and withdraws its `food_log` column: `test_a_day_emptied_in_the_app_is_removed`. Both are in doctor's `_USER_LOGGED_TYPES`: `test_entries_are_not_judged_as_a_stopped_series`. `health_get_food_log` returns them only with `include_entries`, and a default call neither refreshes nor reads them: `test_without_the_flag_it_refreshes_and_reads_the_totals_alone`. **With the flag, `food_log` and both entry types refresh as one**: `refresh_before_query` takes a tuple, and `auto_sync_if_stale` syncs them all when any is stale, so the once-a-day gate does not pair a morning total with afternoon entries. A refresh of one type alone (`live` without the flag, `health_sync`) can still leave them apart until the next day, and a member that keeps failing makes every flagged query re-sync the others; both are accepted. `health_get_breathing_rate` does the same for a night and its summaries. Pinned by `test_with_the_flag_the_three_refresh_together_over_the_window` and `TestSeveralTypesTogether` in `tests/test_refresh_before_query.py`. That tool's entries read is pinned for closing its connection by `test_a_failing_read_of_the_entries_closes_its_connection`
- `authorisation` - id (always 1), missing_scopes (the requested scopes the grant lacked at the last sync that could tell, as JSON names), checked_at. No row, or NULL, is unknown
- `sync_log` - sync history (used by auto-sync to decide when to re-fetch)

**`provider` is on every table above except `sync_log` and `authorisation`**, whose rows are about the sync rather than data from a provider. It names **the provider of the most recent write, not of the row** - an upsert keeps columns the new writer did not name, so a row can hold one provider's efficiency beside another's stage minutes and `provider` says only who wrote last. NULL means no writer has set it, which in practice is a row that arrived by import - `importer` deliberately never names it, and that is what marks a row as imported. **Every sync writer must name it on every write**, or a row it corrects keeps the previous writer's name. Do not "fix" the importer to set it: `_days_another_provider_recorded` identifies imported workouts by `provider IS NULL`, so filling it would silently disable the exercise de-duplication.

**`spo2.avg_ci_low`/`avg_ci_high` are Google's `lowerBoundPercentage`/`upperBoundPercentage`**, described as the bounds of the confidence interval of the night's samples, and not the night's lowest or highest single reading. `min`/`max` hold whatever an import carried; on the data checked, a night carrying both pairs held the same values in each. `sync_spo2` writes only Google's pair, and the read side reports both as stored, leaving any merge to the model reading them. **Never describe the two pairs as different measurements**, and never tell the model not to combine them.

**These columns exist because the same quantity is defined differently by different providers, and merging them would corrupt a series rather than break it.** Never widen one to hold both.

- `cardio_fitness.vo2_max` is a **single value**; `vo2_max_low`/`vo2_max_high` are a reported range. Writing one value into both ends collapses a real band to a point.
- `skin_temperature.nightly_absolute` and `baseline` are absolute degrees C. `nightly_relative` is their difference, which is the quantity the column holds, so a Google reading is stored by subtraction rather than in a column of its own.
- `sleep.sleep_period_minutes` is **not** time in bed. It is `minutesInSleepPeriod`, the delta between bedtime and wake time. It makes a *stated* efficiency computable; do not use it to reconstruct `efficiency`, which has no source in this API and stays NULL rather than being approximated.

**The read side reports each stored series rather than choosing one.** `_trend_cardio_fitness` reports the two VO2 max definitions beside each other with the count of readings behind each (`readings_range` / `readings_single_value`), so a period spanning the switchover says which rows it holds instead of averaging two quantities or ending silently. `_trend_spo2` reports both stored pairs of bounds the same way, as stored rather than merged; `nights_observed_extremes` counts nights carrying an imported pair and `nights_confidence_interval` nights carrying Google's. `avg_nightly_ci_low` is the mean of the nightly bounds, not a confidence interval on the period's average. Pinned by `TestTheTwoSpo2BoundPairs` and `TestTheTwoCardioFitnessDefinitions` in `tests/test_analysis.py`. Compare mode reports the average alone for SpO2 and both VO2 max definitions for cardio fitness; a cardio summary that reads only one definition is the same defect one surface along.

**`_TREND_FNS` and `_COMPARE_QUERY_FNS` must hold the same types**, because the tool's schema is unpacked from the first and `compare=` is served by the second: a type missing from `_COMPARE_QUERY_FNS` is still offered by the schema, and the compare path cannot answer it. That fails as a bare `KeyError`, which is not a `GoogleHealthError`, so `require_auth` does not convert it and the caller is told only `Error executing tool health_trends`. Neither dispatch is derived from `CACHED_DATA_TYPES`, deliberately: `ecg` and `irn` are episodes, and `account`, `height`, `exercise_routes`, `sleep_sessions`, the two reading tables, the day-list tables and `heart_rate_zones` are records, none of them a daily series with a trend. Pinned by `test_the_two_dispatches_offer_the_same_types`, and `test_every_type_the_dispatches_offer_has_a_compare_summary` covers the third list, `summarize`'s own branches, which has no other reader.
