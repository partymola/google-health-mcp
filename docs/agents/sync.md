# The API client, the sync and the write path

Part of the agent guide: [AGENTS.md](../../AGENTS.md) says when to read this file.

- **API**: `api.py` - the Google Health client: `google_get` for one request, `list_google_data_points` and `daily_roll_up` for the two read paths, `list_paired_devices` for the one endpoint that is neither. `list_google_data_points(..., view="reconcile")` reads Google's merge of the sources through the same walk as the per-source list, so paging, 504 halving, the page bound and the deadline are the same code; reconcile paging and its error message are pinned in `tests/test_google_views.py`. `GOOGLE_TYPES` carries each type's three spellings rather than deriving them, because only one of the three fails loudly. Reads and parses in separate steps, and a body that will not decode or is not JSON becomes a `HealthAPIError` saying so. If the parse error were left as the `ValueError` that `json.loads` raises, an intermediary's HTML page would bypass the handlers written for this package's types and land in `run_sync`'s catch-all as an unexpected error. A body nested too deep to parse raises `RecursionError`, which is not a `ValueError`, so every parse of a reply or credential file whose handler names `ValueError` names it too: `tests/test_deep_bodies.py`.
- **Every list here pages to exhaustion**, including devices. A first page carrying a `nextPageToken` is not the whole answer even when it holds no points at all (Google does send such pages), and stopping there drops data with no error. Each walk is bounded by a page count, and the data-point walk by wall clock as well, since both run on the thread serving a tool call.
- **For the types a person logs by hand, the cache holds what Google holds; for the device series a sync adds and corrects and never removes.** A point deleted upstream stops appearing in the API with nothing marking it deleted. **The API gives nothing to detect it by** - measured 16 Aug 2026 against rev 20260805: no tombstone, no change feed, no modified-since filter, and `reconcile` is a cross-source merge rather than change tracking, so a deleted point is simply absent there too. So the hand-logged handlers sweep their window: once a handler has Google's complete answer for [start, end], what this provider wrote for those dates and the answer no longer holds is removed (`_remove_absent`), and on the two daily tables several sources fill, a column whose source no longer answers for a day is withdrawn and a row left with no value is removed (`_withdraw_absent`). **`provider` names only a row's last writer, so on `weight`, which the importer also writes, `google_columns` lists the columns Google wrote and only those are ever withdrawn**: an imported `fat_pct` beside Google's `weight_kg` stays (`test_an_imported_figure_beside_googles_weight_is_never_withdrawn`). A row written before the column existed records none, so nothing on it is withdrawn until Google writes it again. No import writes `food_log`, so it needs no such list. The swept types: `food_entries`, `water_entries`, `food_log`, `core_temperature` (which also clears an edited reading's old key), `weight_readings`, `body_fat_readings`, `weight`, and `exercises` with their `exercise_routes`. A device series is not deleted after the fact, so its handlers never remove anything. **What keeps the sweep from acting on a partial answer**: every walk pages to exhaustion and raises rather than return part of an answer (page bound, deadline, an unreadable page), so a handler that reaches the sweep holds the whole answer; the sweep runs after the last save, so a failed save removes nothing; it touches only rows whose `provider` is this one; it stays inside the dates asked for, never a request's margin; and a point it cannot place removes nothing that run, since it may be one already stored. "Place" is deliberate: a point holds whatever it can be placed under, a reading or a workout by its name and a day by its date, even with no readable value. Only a point the handler cannot place turns the sweep off: a reading or workout with no name, a point with no date for a table kept by day, or a body temperature with no value, since its value is part of its key. So one odd point does not stop deletions for its whole window. Workouts are filtered by Google on their civil start but dated here from the UTC start and offset, so their request carries a day of margin either side, and a workout stored under any date in the window is in the answer if Google holds it. Each removal is logged at INFO as a count, table and dates. What is not closed: a 200 that is wrongly empty would clear the window, and only a sync of those dates brings the rows back, which an ordinary run does only for the last few days; an entry moved in the app to a date before the window leaves its old date and arrives only with `--since` or a rebuild. The one `DELETE` in the package is `db.remove_rows`, pinned by `test_one_function_removes_rows`; the rest in `tests/test_removals.py`. Stated for users under `health_sync` in the README. **The device day-list tables never remove a row, only the points inside one.** Their row is a local day holding that day's points, and a re-sync replaces the day's points, as the nightly `sleep` row replaces its sum, so a point Google no longer sends for a day it still answers leaves the cache, while a day missing from the answer keeps what it had
- **A rebuild fetches [since, until] again for any type, device series included, and only on request.** `sync_tools.rebuild`, served as `health_rebuild` and `google-health-mcp rebuild`, notes every row this provider wrote for those dates, syncs the dates over them in one `_run_sync_types` call, and reports with `_differences` each row that went and each that changed, with values before and after. **Nothing is removed before the fetch**: rows are written over in place, so a value an import put beside Google's stays wherever Google still holds the row (`test_an_imported_value_beside_googles_survives_applying`). `db.watch_writes` puts temporary triggers on the rebuild's own connection, which note the rowid of each row the fetch writes, even with the same values. `db.rows_not_written` then gives the rows Google no longer holds. They are removed, with whatever an import put on them, and reported. Four limits on that removal, each pinned in `tests/test_rebuild.py`. **The fetch carries a day either side, and the rebuild's own removal stays inside [since, until]**, because ECG, sleep and rhythm alerts are filtered by Google on one clock and dated here on another, so a row on the first day can fall outside an answer for exactly those dates (`test_a_reading_on_the_first_day_that_google_files_under_the_day_before_is_kept`). The swept handlers run over the fetched range, so their own sweep can remove on the day either side, as a sync of those dates would; `before` and the report's `range` cover the fetched range for that reason (`test_a_removal_on_the_day_either_side_is_reported`). **Only a row held before the fetch is removed**, since another process can write the cache while the rebuild runs, and the triggers see only this connection (`test_a_row_another_process_writes_meanwhile_is_kept`). **A type whose fetch wrote nothing inside [since, until] has nothing removed**, and carries a `note` when it held rows there: an answer that parses to nothing is more likely a renamed field than every reading gone (`test_an_answer_holding_nothing_it_could_store_removes_nothing`, `test_a_write_on_the_day_either_side_alone_does_not_count_as_an_answer`, `test_a_type_that_held_nothing_carries_no_note`). **Compaction runs after the removals and the report** (`_run_sync_types(..., compact=False)`, then `_compact`): VACUUM may renumber rowids, compaction's own upserts would mark rows as written, and a value it packs would read as changed. **The tables in `_SWEPT_TABLES` are left to their sync.** Its sweep has already removed what Google dropped, and it keeps a point Google still lists even when that point cannot be stored; removing every unwritten row there would undo that. Routes are among them: a held route is not fetched again, and it leaves with its workout. `test_the_tables_left_to_their_sync_are_the_ones_it_removes_from` drives every handler against an empty answer and holds the list equal to the tables each removes from, with `exercise_routes` exempted by hand for that reason. A `weight` row from before `google_columns` records no columns, so neither a sync nor a rebuild withdraws a figure from it. **Without `apply` it runs on an in-memory backup of the cache** and leaves the file alone, so the report is a preview for a person or a model to read before applying; both the tool and the command default to it. A type whose fetch fails has nothing removed. `provider` and `google_columns` are bookkeeping and stay out of the report. A packed column is reported as `(stored compressed)`. Offline it refuses. A rebuild stopped part-way leaves its dates as far as it got. Pinned in `tests/test_rebuild.py`
- **Write path**: every `save_*` goes through `_upsert`, which names only the columns the caller supplied - a named column is updated, an unnamed one keeps its stored value. **Omitting a column and passing it as `None` are different instructions**: the second writes NULL, and is the only way to withdraw a value a provider has retracted, so never collapse the two with `COALESCE(excluded.col, col)`. Column names are interpolated into the statement, so one the table does not have is refused rather than written, as is a row that does not identify itself by its conflict key. `sync_log` is append-only. A refused row raises, which on the sync path lands in `run_sync`'s catch-all and abandons the rest of that data type, loudly. Pinned by `TestAWriterKeepsWhatItDoesNotName` in `tests/test_db.py`. Naming a subset is the normal case, not the exception: `sync_sleep` omits `efficiency`, `sync_activity` omits all five activity-minute columns (`active_minutes` among them), `sync_cardio_fitness` omits the reported range, `sync_heart_rate` omits `zones`, and `importer`'s sleep omits `sessions` and `sleep_period_minutes`. None of those columns has a source any sync reads, so naming it would withdraw whatever a row already held. `heart_rate.zones` is an import's time in zone; Google's `daily-heart-rate-zones` are boundaries alone and go to `heart_rate_zones`, never into that column. `sync_spo2` omits `min`/`max` for a different reason: its bounds go to `avg_ci_low`/`avg_ci_high`
- **`_PACKED_COLUMNS` names the columns stored compressed: `exercise_routes.tcx`, `sleep_sessions.record` and every day-list table's `points`.** They run to kilobytes a row and hundreds of kilobytes a route; the reading tables' `record` is a few hundred bytes and stays text. `_upsert` zlib-compresses the column `_PACKED_COLUMNS` names, so no writer can store it raw, and `_unpacked` inflates it in the query helpers that read one. The value is a BLOB in a column still declared TEXT, because `MIGRATIONS` can only add columns; SQLite stores bytes in a TEXT column unchanged. **Text an earlier release stored reads the same**, and a packed value that will not inflate reads as `None`, like an unparseable JSON column. `db.compact` packs any text left, then runs VACUUM if it packed anything or if a quarter of the file is free pages, so a VACUUM refused while another connection held the file is retried once a quarter of the file is free. **Only `run_sync` calls it, and never in offline mode**: every host opens the cache, and only the syncing one may rewrite it. A release before 1.9.0 cannot read a packed value, so a multi-host setup upgrading past 1.9.0 moves its cache-only hosts first. A release that adds tables moves the syncing host first, because every host's `get_db` creates missing tables on open; the CHANGELOG says which order each release needs. Pinned in `tests/test_packed_columns.py`: `test_a_row_an_earlier_release_stored_as_text_reads_the_same`, `test_every_row_keeps_its_own_text_and_date`, `test_a_cache_only_host_never_rewrites_the_cache` and `test_free_space_an_earlier_run_could_not_reclaim_is_given_back`
- **Google normalisers**: `tools/google_sync.py` - one function per table, all writing through the same upsert. Four rules govern every one of them, and each exists because breaking it produces a plausible wrong number rather than an error. **Integers arrive as JSON strings** (`countSum`, `minutesAsleep`, `beatsPerMinute`), so every numeric field is converted and an unconvertible one is absent, never zero. **A column Google did not report for a day is omitted, not written as `None`** - the upsert reads `None` as "withdraw this", so naming every column unconditionally clears whatever an import left on quieter days. And **absence is not zero except for the quantities where zero is a real reading**: `_TRUE_ZERO_TYPES` names them - Google's own list, from `developers.google.com/health/data-presence-and-true-zeros` - so adding a type forces the decision. A point that yields no column at all writes **no row**, rather than a row of key and provider: such a row stores no measurement, is returned by the query tool as an entry, counts toward compare mode's period counts, and takes the day away from whoever actually put a value in it. `test_no_handler_writes_a_row_that_is_only_a_key_and_a_provider` drives every handler at once, so a new writer with that shape fails without anyone remembering to test it. **Two kinds of column never make a row on their own, by the same reasoning**: `data_source` (the point's `dataSource`, whole, as JSON), which says where a measurement came from rather than measuring anything, and the qualifiers a daily builder names (`_DAILY_QUALIFIERS`: `heart_rate.calculation_method`, and `cardio_fitness`'s level, estimated flag and covariance), which describe a measurement and mean nothing beside an absent one. **Once a measurement is found, both are named on every write, as `None` when the point lacks them**, and so are the measurements only Google writes (each builder's `google_only`: HRV entropy and non-REM rate, SpO2's bounds and spread, and every skin temperature column, since no import writes that table). Those are the only places a daily writer names an absent column: each belongs to the point it arrived with, so one left from an earlier point would sit beside a revised value it was not reported with. None of them is ever written by an import, so the withdrawal costs nothing. Pinned by `test_a_revised_point_withdraws_what_only_google_writes` and `test_a_revised_night_without_a_baseline_withdraws_its_delta`, with `test_an_imported_spo2_pair_survives_a_point_without_bounds` for what must stay. The every-handler test feeds points carrying a source and every qualifier; `test_a_calculation_method_alone_writes_no_row`, `test_a_source_alone_writes_no_row` and `test_a_point_carrying_no_value_stores_nothing` pin the no-row half, and `test_a_revised_rate_withdraws_the_method_and_source_of_the_old_one` and `test_a_revised_value_withdraws_the_qualifiers_of_the_old_one` the withdrawal. Rollups carry no `dataSource`, so the rollup tables have no such column. Enums are stored as the string Google sends (`_text`) and booleans as 1 or 0 (`_flag`), which refuses a string or a number for the same reason `_number` refuses `true`. The day-list writers satisfy it because a row exists only for a day the answer gave points for, and those points are what it stores. The id-keyed writers (`ecg`, `irn`, `exercises`, `exercise_routes`, `sleep_sessions`, the two reading tables, and `account` by resource) satisfy it differently rather than being exempt: a row exists because Google gave the point a name, so it always carries more than its key, and their unreadable fields are written as explicit `None`. `core_temperature` writes its other fields the same way: its key includes the value, so a row always carries a measurement, and a row is one reading rather than a day another writer shares. And **`bool` is a subclass of `int`**, so a JSON `true` casts to 1 with nothing raising; `_number` refuses it, pinned by `test_a_json_true_is_not_a_measurement_of_one`.
- **Sleep aggregation**: a stage the night did not report is **omitted** rather than written as `None`, and so is `total_minutes` when the summary carries none. That only shows on a night that already has stored values - a CLASSIC night arriving over a staged one keeps the old stages instead of clearing them - and it is deliberate, because the realistic transition is stages arriving *late* rather than disappearing. Note also that Google's stage summary counts short awakenings as light sleep, which is worth knowing before comparing `light_minutes` against a series imported from anywhere else.
