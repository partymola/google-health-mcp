# Seams the suite does not cross

Part of the agent guide: [AGENTS.md](../../AGENTS.md) says when to read this file.

A claim sits at a seam when **no input to the program can make its test fail**. Behavioural tests answer "given this input, what happens"; these are about structure, packaging, or which surface an output lands on. Leaks and false invariants collect at them, so check these by execution when they change.

**Assert the defect is absent, not that the fix is present.** A seam test reads source, so it is easy to write one that looks for the shape of the repair - an override exists, a helper is called, a banned word is missing - and every such test is satisfied by a version that reinstates the defect some other way. `log_message` overridden but calling `super()`; a `save_*` helper keeping a dead `_upsert` call beside its own `REPLACE INTO`; a substring check for `INSERT` against SQL that says `REPLACE`. Each of those passes a pin written the first way. The form that holds is a whitelist over what the code may do - no statement executed, no call made, nothing reached outside a permitted expression - because it does not depend on predicting how the next person writes the bad version. **A blacklist here is always one instance behind**, and the second patch to the same predicate is the signal to change shape rather than extend the list.

**An assertion that fails on a correct change is worse than no assertion**, because the cheapest way past it is deletion. A guard that rejects a properly migrated column is this kind - check a new seam assertion against the changes you already intend to make.

Crossed, and by what:

- **Closures that cannot be imported.** `CallbackHandler` lives inside `setup_google_auth`, so the only way to check it is to read the source. `TestTheCallbackPage` does, pinning three properties across its five tests: the page escapes what it shows, every `wfile` write goes through `_callback_page`, and the exception reaches the user only as `type(e).__name__` and is never reached unbound. It parametrises over every `setup_*` function it can discover rather than naming one, so a second flow added beside it inherits the pins instead of quietly having none.
- **The module import graph.** No behavioural test can see an unused import, and `doctor` importing `auth` or `api` would let a diagnostic rotate a token another host owns. `TestDoctorStaysOffline`.
- **Which code may print a path.** `test_no_logger_call_in_shared_code_carries_a_path` in `tests/test_seams.py`. Key on the logging *method*, not on the receiver's name - `logging.getLogger(__name__).info` is the same call as `logger.info` and a name match misses it. Inside `api.py` alone, a call to `_operation(...)` is exempt, because that function reduces a request path to a data type and method. Binding a path to another variable name also gets past the check, so never do that to silence it.
- **Packaging consistency.** `test_the_declared_version_and_the_lockfile_agree`, same file.
- **A doc restating a list the code holds.** Unpinned, a README scope table goes on telling readers to tick a scope the code has dropped, because a fact kept in two places gets edited in one. `test_the_readme_scope_table_is_the_scopes_that_are_requested` reads the table and compares it with the constant, and reads the paragraph beneath it separately - that one names the scopes this package declines, which is the opposite claim, so it must stay disjoint from what is requested. Either derive such a list or pin it this way; do not leave it to be noticed.
- **Which data type a fetch is given.** Every normaliser test mocks the client, so a path travels no further than the mock: replacing `"sleep"` with a type that does not exist leaves every behavioural test green while the real sync 404s and that table stops filling. `test_every_data_type_a_fetch_names_is_one_the_api_has` reads the literal each fetch is handed and checks it against `GOOGLE_TYPES`. The scope equality in [auth.md](auth.md) catches it too, but only where `GOOGLE_SCOPE_READERS` is not edited to match; this one fires either way.
- **Whether a tool a module defines ever reaches the wire.** Registration is a decorator that runs at import time, so a module `cli.py` does not name registers nothing: its tools are absent while the suite imports the module directly and every behavioural test on it passes. `test_every_tool_written_here_reaches_the_wire` asks the server's own registry, not the import list - a test that read `cli.py`'s imports would pass a tool registered by some other call and fail a correct change to how modules are discovered.
- **The lists a schema change has to move together.** A column added to `SCHEMA` reaches an existing database only if `_migrate` alters the table; miss that and `doctor` grades the database FAIL and tells a user with a long history to re-create it, for something an `ALTER` would have fixed. Adding a column with no migration passes every behavioural test. `TestTheMigrationLockstep` in `tests/test_seams.py` opens each file in `tests/schema_baselines/` and asserts the result matches `SCHEMA` exactly. `doctor._SELF_HEALING_COLUMNS` is *derived* from `db.MIGRATIONS` rather than restated, so it cannot be missed on its own; `test_self_healing_columns_is_exactly_what_migrate_adds` still earns its place by catching an entry whose `ALTER` adds nothing.
  - **Removing or renaming a column is not expressible.** `MIGRATIONS` is add-only, so a baseline database keeps the column forever while the lockstep asserts set equality - the only green route is deleting the baseline, which drops support for that release. Decide that deliberately rather than reaching for it under a red test.
  - **A baseline exists from 1.0.0 onwards, and `test_a_released_schema_is_always_on_file` is what keeps it that way.** With the directory empty every other test in the class iterates nothing and passes - which is what a package looks like before its first release, and it is when the hole is widest: a column added to `SCHEMA` then satisfies the whole suite, and the user who upgrades into it is told by `doctor` to re-create three years of rows. Data from elsewhere arrives through `importer`, which writes rows through this package's own writers rather than adopting another database's shape, so `MIGRATIONS` stays about our own history alone.
  - **Each baseline is `SCHEMA` as a release shipped it, named `X.Y.Z.sql`, and is written once.** It is added at *release* rather than when `SCHEMA` changes, so that every file describes a version somebody could be running rather than a state that only ever existed mid-branch. The procedure is in CONTRIBUTING's release steps; deleting one drops support for databases that old.
  - **Editing one is the escape hatch from a red lockstep, and only history can see it.** `test_no_older_baseline_has_been_refreshed_to_the_current_schema` exempts the newest file, which equals `SCHEMA` whenever nothing has changed since the last release - so with a single baseline on file, refreshing it to match a new column turns the whole class green. `test_no_baseline_has_been_changed_since_it_was_added` asks git **how many commits have touched each file**, not for a diff against HEAD: the maintainer commits the edit, after which the worktree and HEAD agree forever and a diff could never fire in CI. It says nothing about a baseline being added or deleted, which are the release step and the documented way of dropping support. It skips without git, without a checkout, on a shallow clone (one commit per file whatever the history), and while no baseline is committed.
  - **One baseline is not enough, and the gap is invisible.** A table the baseline predates is created whole by `CREATE TABLE IF NOT EXISTS`, so a column added to *that* table satisfies a single-baseline check while still breaking the database of a user who has the table and not the column - and the same check then rejects the correct migration, pointing a maintainer at exactly the wrong repair. Covering every released vintage is what makes a green run mean what it says.
- **Two more lists that restate `SCHEMA`'s tables.** A table absent from `_UPSERT_KEYS` raises inside `_upsert`, which on the sync path `run_sync`'s catch-all records as an exception type; one absent from `_DATA_TABLE_MAP` is quieter still, re-fetching its whole window every run with nothing looking wrong. `test_every_table_is_accounted_for_by_the_lists_that_enumerate_them` names the excluded tables rather than inferring them.
- **That every `save_*` actually writes through `_upsert`.** Most upserted tables have no preservation test, so a helper reverted to its own `INSERT OR REPLACE` keeps its `_UPSERT_KEYS` entry and passes the whole suite while the entry means nothing. `test_no_save_helper_reaches_the_database_except_through_the_upsert` reads the source and pins both directions.
- **Whether the harness lets a test reach the network, or see this machine's credentials or cache.** Deleting `_no_network` fails its pin anywhere. Deleting `_no_real_credentials` fails nothing wherever no credential exists, which is what CI is; on a machine holding one it fails its own pin and takes tool tests with it. `test_the_suite_cannot_reach_the_network` pins the first, `test_the_suite_cannot_see_real_credentials` the second and `test_the_suite_cannot_see_the_real_cache` the third; no one test covers another. See "Running tests" in [AGENTS.md](../../AGENTS.md#running-tests) for why the refusal is `pytest.fail` and why `helpers` is patched as well as `config`.
- **Whether an exception's message survives the trip to the model.** The conversion happens in `require_auth`, a layer above the one every tool test calls, so a class that forgets the `GoogleHealthError` base raises fine, is caught fine, and passes everything behavioural while reaching the client as a bare `Error executing tool <name>`. `test_every_exception_this_package_defines_reaches_the_model` walks the package's own classes and asks the hierarchy rather than reading the `class` statement, and names its exclusions in `_NOT_MODEL_FACING` so leaving the base off has to be a decision. Three things about how it walks are load-bearing. Two are pinned, each measured by removing it and watching a bad class go unreported: it keys each class by its module and name, or a conforming class shadows a broken one of the same name in another module; and it seeds itself with the package module, since `walk_packages` yields what is *inside* the directory and never `__init__.py`. The third, `onerror`, has no mutant that distinguishes it from its own deletion while `tools` is the only subpackage, because the test imports that one directly before the walk would recurse into it; it guards a nested subpackage the layout does not have yet, so do not read it as pinned. **It sees classes this package defines, not raise sites**: a bare `RuntimeError` or `ValueError` raised here is masked and nothing reports it, which is why `refresh_before_query` raises `LiveRefreshFailed` rather than a bare `RuntimeError`.
- **Which modules hold a credential path of their own.** `_no_real_credentials` patches a fixed pair of modules, and a new one importing these names by value escapes it in silence, keeping the real paths while every other signal says the suite is isolated. Nothing on CI can see it: with no credential present there is nothing to observe either way. `test_only_the_expected_modules_hold_a_config_path`.

Crossed only from outside this repo, which an outside contributor will not have:

- **The mock boundary.** Tool and normaliser tests patch the client's own functions, so the mock sits above the real client and the shape it hands back is agreed between two mocks rather than measured. Partially crossed by `TestTheArrayEndpointsSurviveTheRealClient`, which drives `devices` and one Google normaliser from the response body up - the pattern to copy when a change touches that layer.
- **The wire contract, for every tool but one.** Most of the suite calls tool functions directly rather than through the server, so a tool's description and its input schema are untested: replacing a docstring with nonsense, or changing a parameter's type annotation, passes the whole suite. A rename is caught, but only incidentally, since `tests/test_tools.py` imports the functions by name. Do not read that as contract coverage. Dump the tool list and schemas from a real server and diff them across the change. **`health_trends` is the exception**: `tests/test_argument_validation.py` asks `mcp.list_tools()` for its schema and drives it through `mcp.call_tool`, so relaxing either of its enumerated annotations fails there rather than shipping. That covers the schema and not the description, and it covers one tool and not the rest. `tests/test_date_ranges.py` drives every date tool over the same path, but only for its date refusals.
- **The pre-commit guard.** `scripts/check-no-data.sh` is not run by any test or by CI. To check a change to it, work in a throwaway clone: stage one probe per class it should refuse, plus one it should pass, using `git add -f` for gitignored paths, and compare the script's exit code with what you expect.
