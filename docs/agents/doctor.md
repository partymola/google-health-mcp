# Doctor and the staleness checks

Part of the agent guide: [AGENTS.md](../../AGENTS.md) says when to read this file.

- **Two staleness checks, and they are deliberately different questions.** `_check_freshness` judges the newest date **across all types**, because types written only when the user logs something lag by design and flagging them individually cries wolf. That leaves one type dying while the rest continue invisible - which is this package's worst silent failure: a response field renamed upstream makes every page parse to nothing while the request still succeeds, so a table stops filling with `sync_log` recording `ok` and zero rows. `_check_stopped_series` covers exactly that gap. **Density is what tells a stopped series from a sporadic one**: a type is judged only if it filled at least `_ESTABLISHED_DAYS` of the `_STOPPED_PRIOR_DAYS` before **its own last row** - not before the recent window, which is the same measurement anchored to the wrong end and would make the check go blind about a month after the failure it exists to catch, reporting a clean bill of health from then on. **Density alone is not enough**, and `_USER_LOGGED_TYPES` is why (with `_UNJUDGED_DEVICE_TYPES`, the device series whose gaps are ordinary, under the day-list tables in [schema.md](schema.md)): for a type a person fills by hand it measures a habit rather than a device, and a month of logged runs followed by a month off is not a fault, so those types are excluded by name. The recent window is 14 days, set a few days above the longest gap seen in a year of a worn device's data (the longest gaps are in the nightly series: SpO2, skin temperature, HRV and breathing rate), so ordinary wear does not read as a stop while a real one is caught within a fortnight. An occasional longer gap is the accepted cost. Graded WARN, never FAIL: a series can also stop because the user stopped wearing the watch. **The remediation must name `--since`**, never `--days`, which is read only when there is no cursor and so is inert for exactly the series being diagnosed. Pinned by `TestASeriesThatHasStopped` in `tests/test_doctor.py`
- **A series no successful sync has ever filled is exempt, because otherwise the finding is permanent and a permanent finding is not a finding.** Density cannot tell a row this package wrote from one that arrived another way, so a type whose rows all came from elsewhere reads as a dense series that stopped on the day those rows end - correct, unclearable, and the state the report then spends its life in. Where an external monitor matches `STOPPED_SERIES` the finding also holds that monitor down, which on a monitor carrying other signals silences those too, and this has happened in practice. `_never_filled_types` answers it from `sync_log`, and the query's own conditions are the specification - read them there rather than restating them here, or the two drift. **The exemption is on positive evidence only**: a type absent from `sync_log`, or whose total is not a measured count, is unknown and judged by density alone, whether the cache predates this check or was written by another program. **The finding says only that no successful sync wrote those rows, and must never say where they came from** - "imported" is the benign branch of the ambiguity this whole check exists to doubt, since a normaliser reading a renamed field leaves identical evidence, and a finding that picks it talks the reader out of the fault. **It carries `SERIES_NEVER_FILLED`**, because a monitor gating on `STOPPED_SERIES` otherwise sees that condition vanish and cannot tell recovery from a build that stopped judging it. **Do not reach for `provider IS NULL` instead**: `core_temperature.provider` was never written before 1.7.0, so a synced reading from before then holds NULL until its window is re-synced, and a provider test misjudges it. **And do not drop the exempt type from the report** - a check that goes quiet about a type reads as one that has gone blind. The function's docstring carries three limits that are real and not closable here, including that rebuilding the cache retires the evidence. Pinned by `TestASeriesThisSyncHasNeverFilled` in `tests/test_doctor.py`
- **Doctor**: `doctor.py` - the `doctor` subcommand. Every check is offline and read-only, and two properties are load-bearing rather than incidental: it never opens the database through `db.get_db()` (which would create it and destroy the evidence for the wrong-path and stale-cache checks), and it imports only `config` and `db` - never `auth` or `api`, so no code path can rewrite a token file that another host owns. Keep both true when adding a check. **Two of the permission findings cannot fire on Windows**, because `os.access` there is a `GetFileAttributes` test rather than a permission one: `R_OK` is satisfied by existence alone, and a directory is never read-only. So the unreadable-database branch and the directory half of the unwritable-database check are unreachable, and the tests asserting them skip rather than being made to pass. The third does fire - `W_OK` on a file reflects the read-only attribute, which is what `test_reports_an_unwritable_token_file` sets - but it reflects only that attribute and never an ACL. A database an ACL denies still reports, through the branch for an open that failed, which says the contents are not implicated: the gap is a missing diagnosis, never a wrong one
- **`Finding.check` is the only part of `doctor`'s output that is an interface.** `name` and `detail` are prose written for a person and interpolate the data type, so nothing outside can match on them; `check` is a stable slug, emitted by `doctor --json` and `null` for findings nothing consumes yet. **Adding one is free; changing one is a breaking change that fails silently at the consumer**, because a slug no finding carries reads as "that condition is not present" rather than as an error. `STOPPED_SERIES` is the first, and it exists because `doctor` exits non-zero only on FAIL while a stopped series is graded WARN - so the exit code structurally cannot carry the condition an external monitor most needs. That grading is deliberate and must not be raised to FAIL to make it visible: a series can stop because the device stopped being worn. Pinned by `TestTheMachineReadableReport` in `tests/test_doctor.py`, which asserts the slug survives a rename of the human-readable name and that a WARN never moves the exit code in either format, and by `test_doctor_json_flag_emits_json_on_stdout` in `tests/test_cli.py`. **Both layers need pinning and it is easy to stop at one**: testing `format_json` proves the formatter, `run_doctor(as_json=...)` proves the selection, and only the CLI test proves the flag is wired - with that missing, deleting the `add_argument` block, dropping the argument at the call site, or flipping it to `store_false` all ship green. The README's example payload is held to the emitted shape by `test_the_readme_json_example_matches_what_doctor_emits` in `tests/test_seams.py`
