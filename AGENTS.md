# google-health-mcp - agent guide

`CLAUDE.md` symlinks to this file. It orients AI agents and contributors working *in* the code, and deliberately does not repeat the user-facing docs:

- **What it is, install, auth, tools, config, CLI, usage** -> [README.md](README.md)
- **Dev environment, running tests, pre-commit hook, PR & security process** -> [CONTRIBUTING.md](CONTRIBUTING.md)

**This is a public open-source repository and health data is sensitive PII.** Read the Data Safety Rules before committing.

## Data Safety Rules

Before committing ANY change, verify:

- **No real health measurements** in code, tests, commits, or docs - no real heart rates, sleep data, step counts, weight, SpO2, or HRV values
- **No personal identifiers** - no real names, account or user ids, or dates of birth
- **No credentials** - no OAuth tokens, client IDs, API keys, or token files
- **Test fixtures must use fictional data** - obviously fake values and fixed past dates (e.g. 2026-03-10)
- **Error messages and logs**: status codes and operation names only - never measurement values or API response bodies. Filesystem paths are governed separately, under Auto-sync behaviour: a CLI subcommand may print one, shared code may not
- **`config/` and `*.db` are gitignored for a reason** - never override this

The `scripts/check-no-data.sh` pre-commit hook rejects database files, config secrets, and large files automatically. Install it per [CONTRIBUTING.md](CONTRIBUTING.md).

## Architecture

- **Entry point**: `src/google_health_mcp/cli.py` - routes `auth`/`sync`/`import`/`doctor` subcommands or starts the MCP stdio server. `sync` takes `--since`/`--until` to backfill or re-fetch a date range; `import` (backed by `importer.py`) bulk-loads exported data
- **MCP server**: `mcp_instance.py` creates the shared `MCPServer("google-health-mcp")` instance
- **Auth**: `auth.py` - Google OAuth setup and token refresh. Access tokens last an hour; refresh tokens do not rotate, which is what lets a token minted on a machine with a browser be copied to a headless one. Scopes are `GOOGLE_SCOPES` in `config.py`; after widening them, re-run `google-health-mcp auth`. Where the list comes from and why is stated once, in `config.py` beside the constant. Every requested scope names the data types fetched under it in `_SCOPE_READERS`, and `test_no_scope_is_asked_for_that_nothing_reads` asserts that set is *equal* to what the sync fetches, in both directions: a scope with no reader is a permission the user grants for nothing, and a scope deleted while something still fetches its types is a 403 that reads like a publishing problem. Both prose and a one-sided `any(...)` failed to hold it. `_save_json`'s `hasattr(os, "fchmod")` asks whether the call exists, not whether this is POSIX, and since 3.13 it exists on Windows too - where it is not a no-op but sets the read-only attribute from the owner-write bit, so at 0o600 it clears it. Nothing there restricts the file to one account on Windows; do not read the guard as meaning the call is skipped there. **The callback listener is `_CallbackServer`, not a bare `HTTPServer`, and that matters on Windows.** `HTTPServer` sets `allow_reuse_address`, which on POSIX only waives TIME_WAIT. On Windows it is consent to be displaced: per Microsoft's same-user table for a specific-address bind, a first socket holding the address with `SO_REUSEADDR` is bound over by a second one asking for the same, so another process could take the authorisation code - which is enough to obtain the tokens. **Not asking is what closes it** - the same table shows a first bind with neither option refusing that second bind. `SO_EXCLUSIVEADDRUSE` is asked for as well because Microsoft recommends it for server sockets and because it is the half that would still hold for a wildcard bind, which this listener is not. Never ask for both: reuse requested after exclusive use is the configuration Microsoft calls insecure, and `allow_reuse_port` (the POSIX-side equivalent hazard) is pinned off for the same reason. The cost is Windows-only - the port stays held until the previous connection has finished closing, normally a couple of minutes, and `auth` has to be retried until it has - which is also why `setup_google_auth` catches the resulting `OSError` and binds before opening the browser rather than after. `doctor`'s port probe asks for reuse on POSIX only, for the matching reason; the two must stay in step. `TestTheCallbackPortIsNotShared` in `tests/test_auth.py` drives the Windows branch on a POSIX runner against a recording socket rather than reading the source for it - source assertions here let the option be set after the bind, at the wrong level, on the wrong socket, or with a value of 0, all of which pass a check that only looks for the name
- **API**: `api.py` - the Google Health client: `google_get` for one request, `list_google_data_points` and `daily_roll_up` for the two read paths, `list_paired_devices` for the one endpoint that is neither. `GOOGLE_TYPES` carries each type's three spellings rather than deriving them, because only one of the three fails loudly. Reads and parses in separate steps: a body that will not decode or is not JSON raises `ValueError`, which no transport handler catches, so combining them let an intermediary's HTML page escape `run_sync` with no `sync_log` row.
- **Every list here pages to exhaustion**, including devices. A first page carrying a `nextPageToken` is not the whole answer even when it holds no points at all - measured, and it is what made a month of steps read as absent. Each walk is bounded by a page count, and the data-point walk by wall clock as well, since both run on the thread serving a tool call.
- **Failure classification**: `refresh_google_token` is a boundary over `_refresh_google_token` and raises exactly two types. `TokenRefused` only where the server or the credential files judged the credentials unusable; `RefreshNetworkError` for everything else, via a catch-all, so an unanticipated failure lands there by construction rather than by listing exception types. `google_get` maps the first to `HealthAuthError`, which `doctor` grades FAIL and answers with "run auth" - rotating the token file the syncing host owns - and the second to `HealthAPIError`, which grades WARN. (In offline mode `doctor` grades both WARN: a token cannot be checked without the network.) **Never widen `TokenRefused` to a condition that can clear on its own** (a rate limit, a 403 from a WAF, an unreadable response). Pinned by `TestTheGoogleRefreshBoundary` in `tests/test_google_auth.py`, and at the client by `TestTheTokenLayerIsClassified` and `TestAgainstTheRealGoogleRefresh` in `tests/test_google_api.py`. Note: nothing in the sync layer sleeps on a 429 - a rate limit surfaces as a `rate_limited` status for that type and the next run resumes from the cursor
- **DB**: `db.py` - SQLite schema (one table per cached data type + `sync_log`), save/query helpers
- **Write path**: every `save_*` goes through `_upsert`, which names only the columns the caller supplied - a named column is updated, an unnamed one keeps its stored value. **Omitting a column and passing it as `None` are different instructions**: the second writes NULL, and is the only way to withdraw a value a provider has retracted, so never collapse the two with `COALESCE(excluded.col, col)`. Column names are interpolated into the statement, so one the table does not have is refused rather than written, as is a row that does not identify itself by its conflict key. `core_temperature` is not upserted - keyed by (datetime, temp_celsius), a changed reading is a new row rather than a correction, so it keeps `INSERT OR IGNORE` - and `sync_log` is append-only. A refused row raises, which on the sync path lands in `run_sync`'s catch-all and abandons the rest of that data type - loud, and a change from the old binding, which ignored a key the table did not have. Pinned by `TestAWriterKeepsWhatItDoesNotName` in `tests/test_db.py`. Naming a subset is the normal case, not the exception: `sync_sleep` omits `efficiency`, `sync_spo2` omits `min`/`max`, `sync_activity` omits all five activity-minute columns (`active_minutes` among them - it was a derivation of two of the others, so it goes with them), `sync_cardio_fitness` omits the reported range, `sync_heart_rate` omits `zones`, and `importer`'s sleep omits `sessions` and `sleep_period_minutes`. Each of those columns has no source in this provider, so naming it would withdraw whatever a row already held
- **Google normalisers**: `tools/google_sync.py` - one function per table, all writing through the same upsert. Four rules govern every one of them, and each exists because breaking it produces a plausible wrong number rather than an error. **Integers arrive as JSON strings** (`countSum`, `minutesAsleep`, `beatsPerMinute`), so every numeric field is converted and an unconvertible one is absent, never zero. **A column Google did not report for a day is omitted, not written as `None`** - the upsert reads `None` as "withdraw this", so naming every column unconditionally clears whatever an import left on quieter days. And **absence is not zero except for the quantities where zero is a real reading**: `_TRUE_ZERO_TYPES` names them - Google's own list, from `developers.google.com/health/data-presence-and-true-zeros` - so adding a type forces the decision. A point that yields no column at all writes **no row**, rather than a row of key and provider: such a row stores no measurement, is returned by the query tool as an entry, counts toward compare mode's period counts, and takes the day away from whoever actually put a value in it. `test_no_handler_writes_a_row_that_is_only_a_key_and_a_provider` drives every handler at once, so a new writer with that shape fails without anyone remembering to test it. The id-keyed writers - `ecg`, `irn`, `exercises` - satisfy it differently rather than being exempt: a row exists because Google gave the point a name, so it always carries more than its key, and their unreadable fields are written as explicit `None`. And **`bool` is a subclass of `int`**, so a JSON `true` casts to 1 with nothing raising; `_number` refuses it, pinned by `test_a_json_true_is_not_a_measurement_of_one`.
- **Sleep aggregation**: a stage the night did not report is **omitted** rather than written as `None`, and so is `total_minutes` when the summary carries none. That only shows on a night that already has stored values - a CLASSIC night arriving over a staged one keeps the old stages instead of clearing them - and it is deliberate, because the realistic transition is stages arriving *late* rather than disappearing. Note also that Google's stage summary counts short awakenings as light sleep, which is worth knowing before comparing `light_minutes` against a series imported from anywhere else.
- **Tools**: `tools/` - domain-grouped modules; `sync_tools.py` also exports `auto_sync_if_stale(data_type)`. A module reaches the wire only by being imported in `cli.py`. **`health_get_ecg` returns a reading's waveform only when asked for it**: thousands of voltages is a useless tool response and an expensive one, so the default carries the summary plus a sample count, which is `null` rather than 0 where no trace was stored. That is a constraint on the tool, not on what is cached. Pinned by `TestTheWaveformStaysBehindItsFlag` in `tests/test_rhythm.py`
- **Helpers**: `helpers.py` - `require_auth` (auth-gate decorator on every tool), plus `format_response`/`parse_date`. **`require_auth` is the one place an exception that *escapes* a tool keeps its message.** (`run_sync` also returns `str(e)` inside its own payload, which is a different route and is governed above.) `mcp` 2.1 keeps a `ToolError`'s text and replaces every other exception's with `Error executing tool <name>`, so a `GoogleHealthError` is converted and nothing else is. The split follows the leak rules above: this package writes the messages it raises deliberately, while an unplanned failure's text is exactly what must not travel, since a socket error names an absolute path. **Never widen the conversion to `Exception`.** It would undo that in one line and the suite would stay green. `HealthOfflineError` keeps a clause before it, because offline mode answers with one clean message rather than an error. Pinned by `TestWhichErrorsAreExplainedToTheModel` in `tests/test_tools.py`, in both directions: `test_an_unplanned_error_is_left_to_be_masked` is the half that fails if the conversion is widened. **Membership in the base is not a promise about the message**, and one raise site shows why: `_load_google_client` interpolates the resolved client path into a `TokenRefused`, which is deliberate for `google-health-mcp auth` where that path is the useful part, and is kept off the wire by `google_get` catching that type and re-raising `HealthAuthError`, pinned by `test_neither_message_carries_the_original`. A tool calling `refresh_google_token` directly would publish it
- **Config**: `config.py` - paths overridable via `GOOGLE_HEALTH_MCP_CONFIG_DIR` and `GOOGLE_HEALTH_MCP_DB_PATH`; `GOOGLE_HEALTH_MCP_OFFLINE` for cache-only mode
- **Two staleness checks, and they are deliberately different questions.** `_check_freshness` judges the newest date **across all types**, because types written only when the user logs something lag by design and flagging them individually cries wolf. That leaves one type dying while the rest continue invisible - which is this package's worst silent failure: a response field renamed upstream makes every page parse to nothing while the request still succeeds, so a table stops filling with `sync_log` recording `ok` and zero rows. `_check_stopped_series` covers exactly that gap. **Density is what tells a stopped series from a sporadic one**: a type is judged only if it filled at least `_ESTABLISHED_DAYS` of the `_STOPPED_PRIOR_DAYS` before **its own last row** - not before the recent window, which is the same measurement anchored to the wrong end and made the check go blind about six weeks after the failure it exists to catch, reporting a clean bill of health from then on. **Density alone is not enough**, and `_USER_LOGGED_TYPES` is why: for a type a person fills by hand it measures a habit rather than a device, and a month of logged runs followed by a month off is not a fault, so those types are excluded by name. The recent window is 14 days: the longest gap in the last 400 days of a real cache is 11 (skin temperature, SpO2), so that is a three-day margin, and the 19 and 20-day gaps further back in HRV and breathing rate are the accepted cost of detecting a real stop within a fortnight. Graded WARN, never FAIL: a series can also stop because the user stopped wearing the watch. **The remediation must name `--since`**, never `--days`, which is read only when there is no cursor and so is inert for exactly the series being diagnosed. Pinned by `TestASeriesThatHasStopped` in `tests/test_doctor.py`
- **Doctor**: `doctor.py` - the `doctor` subcommand. Every check is offline and read-only, and two properties are load-bearing rather than incidental: it never opens the database through `db.get_db()` (which would create it and destroy the evidence for the wrong-path and stale-cache checks), and it imports only `config` and `db` - never `auth` or `api`, so no code path can rotate a refresh token that another host owns. Keep both true when adding a check. **Two of the permission findings cannot fire on Windows**, because `os.access` there is a `GetFileAttributes` test rather than a permission one: `R_OK` is satisfied by existence alone, and a directory is never read-only. So the unreadable-database branch and the directory half of the unwritable-database check are unreachable, and the tests asserting them skip rather than being made to pass. The third does fire - `W_OK` on a file reflects the read-only attribute, which is what `test_reports_an_unwritable_token_file` sets - but it reflects only that attribute and never an ACL. A database an ACL denies still reports, through the branch for an open that failed, which says the contents are not implicated: the gap is a missing diagnosis, never a wrong one
- **`Finding.check` is the only part of `doctor`'s output that is an interface.** `name` and `detail` are prose written for a person and interpolate the data type, so nothing outside can match on them; `check` is a stable slug, emitted by `doctor --json` and `null` for findings nothing consumes yet. **Adding one is free; changing one is a breaking change that fails silently at the consumer**, because an absent key reads as "that condition is not present" rather than as an error. `STOPPED_SERIES` is the first, and it exists because `doctor` exits non-zero only on FAIL while a stopped series is graded WARN - so the exit code structurally cannot carry the condition an external monitor most needs. That grading is deliberate and must not be raised to FAIL to make it visible: a series can stop because the device stopped being worn. Pinned by `TestTheMachineReadableReport` in `tests/test_doctor.py`, which asserts the slug survives a rename of the human-readable name and that a WARN never moves the exit code in either format, and by `test_doctor_json_flag_emits_json_on_stdout` in `tests/test_cli.py`. **Both layers need pinning and it is easy to stop at one**: testing `format_json` proves the formatter, `run_doctor(as_json=...)` proves the selection, and only the CLI test proves the flag is wired - with that missing, deleting the `add_argument` block, dropping the argument at the call site, or flipping it to `store_false` all ship green. The README's example payload is held to the emitted shape by `test_the_readme_json_example_matches_what_doctor_emits` in `tests/test_seams.py`

## Auto-sync behaviour

`get_*` reach `auto_sync_if_stale(data_type)` through `refresh_before_query`, and `health_trends` calls it directly, before querying: it triggers an incremental sync if the last successful sync for that data type was before today (checked via `sync_log`), at most once per data type per day. Failures are swallowed silently - the cache query proceeds regardless.

That silence is why `run_sync` ends its per-type loop with a catch-all writing an `error` row: `sync_log` is the only record any failure leaves, and anything escaping the named handlers escapes into that bare `except`, leaving `doctor` reporting a clean log while the cache ages. **Keep the catch-all, and keep the row's notes to the exception type** - these paths carry API responses, and a message built from one could hold anything. The row is best-effort: writing it is itself a database write, and on a read-only database it fails too, so it is wrapped and the connection is closed in a `finally` around the whole loop rather than per handler. Pinned by `test_an_unnamed_failure_still_leaves_a_sync_log_row`, `test_the_unnamed_failure_message_carries_no_response_content` (both assert the note by equality - a substring check passes with the exception interpolated) and `test_a_database_that_cannot_record_the_failure_does_not_escape`, in `tests/test_sync.py`.

**Nothing built from an API response or an exception's own text reaches a user, a log or `sync_log`.** `run_sync` writes `str(e)` straight into `sync_log.notes` and returns it to the client, so every exception the client raises carries fixed text plus at most a status code and a request path. Not the response body - an error body can quote the measurement that caused it - and not the underlying exception, whose text for a TLS or socket failure is an absolute path. The same rule governs `auth.py`'s callback page and `auto_sync_if_stale`'s debug line, which report `type(e).__name__` for that reason - do not restore `exc_info=True` there. Pinned by `test_no_part_of_the_error_body_reaches_the_message` and `test_a_transport_failure_carries_no_path` in `tests/test_google_api.py`, by `test_auto_sync_logs_a_type_rather_than_a_traceback` in `tests/test_sync.py`, and for the interactive setup flow by the two source-reading assertions in `TestTheCallbackPage`: the exception may travel only as `type(e).__name__`, and the live exception may not be reached without binding it at all (`traceback.format_exc`, `sys.exc_info`, `locals`, a bare `except:`).

**A resumed sync starts `INCREMENTAL_OVERLAP_DAYS` behind its cursor, not at it, and that is load-bearing.** Google publishes a day's `daily-*` summary after the day has ended, so a sync running late in the local day finds nothing for yesterday and still records that it attempted through today; resuming from that cursor would never ask for yesterday again. **Measured on a real cache**: `resting_hr`, `breaths_per_min`, `nightly_relative` and `spo2.avg` each had no 19 Aug 2026 row while Google held one for each, and a re-fetch of exactly that window returned all four - so the day was lost to the cursor, not missing upstream. Nothing reported it, because `sync_log` was full of `ok`, which is what `doctor` grades. With an hourly sync the hole was wider than that measurement alone shows: after the first run of a day the cursor is already today, so every later run that day asked for `[today, today]` and no earlier day could ever be revisited. The property the constant buys, stated so the value can be re-derived: **a day is asked for again on every run from that day through `INCREMENTAL_OVERLAP_DAYS` later, so the overlap tolerates a publication lag of up to that many days** - measured at one, with the rest as margin. It is not about a host being off, which needs none of it: `last_date_attempted` is written only on success, so the cursor does not advance while nothing runs. The overlap is bounded because that cursor exists to stop a type nobody records any more being re-queried from its last reading on every run forever, and the upsert makes the repeated days free of consequence. Pinned by `TestTheIncrementalWindowLooksBack` in `tests/test_sync.py`.

**Filesystem paths are a narrower rule than the one above, because two subcommands print them deliberately.** `doctor` exists to report which paths it resolved, and `import` names the directory it was given and the database it wrote to. Both are commands a person typed, and their output - stdout or stderr - is that person's terminal. **`doctor --json` widens that destination without widening the rule**: the payload carries the same resolved paths, and it is meant to be read by a program that may forward it off the host, so a consumer that does so owns that disclosure. What must stay true either way is the harder half - no credential value and no measurement reaches either format, pinned for both by the parametrised `test_never_prints_token_or_secret_values`, which drives the credential files the code actually opens - fictional ones, under `_no_real_credentials` - rather than hand-built findings. A leak test that builds its own findings never puts a secret anywhere and passes over code that dumps the whole token file.

Everything else must not carry one, and that includes every `logger.*` call. Logging is shared by both modes: run with no subcommand, the process speaks JSON-RPC on stdout and its log lines go to stderr, where the MCP client collects them, so a log line is closer to a tool response than to a terminal. The test for a new path is therefore **which code prints it, not which stream**: a CLI subcommand may, shared code may not. `sync_log.notes` and every tool response may not either, because both are stored or handed to the model. That is why `importer` prints the directory it was given and logs only a file's name.

Three ordering rules in `run_sync` are load-bearing and easy to undo. `HealthOfflineError` must keep a clause of its own before the trailing catch-all, or offline mode turns into per-type error rows instead of one clean message; it no longer closes the connection, because the `finally` does. A failure is logged `auth_error` rather than `error` because `doctor` grades the two differently and a dead token is the one that will not clear itself. And the wait a 429 asks for is clamped to `api.MAX_RATE_LIMIT_WAIT` where the header is read, so a caller that ever sleeps on it cannot be handed an unbounded or unparseable value - nothing sleeps on it today. Pinned by `test_offline_error_propagates_and_closes` and the `TestTheRateLimitWait` cases.

## Seams the suite does not cross

A claim sits at a seam when **no input to the program can make its test fail**. Behavioural tests answer "given this input, what happens"; these are about structure, packaging, or which surface an output lands on. Every leak and every false invariant found in this repo has been at one of them, so check these by execution when they change.

**Assert the defect is absent, not that the fix is present.** A seam test reads source, so it is easy to write one that looks for the shape of the repair - an override exists, a helper is called, a banned word is missing - and every such test is satisfied by a version that reinstates the defect some other way. `log_message` overridden but calling `super()`; a `save_*` helper keeping a dead `_upsert` call beside its own `REPLACE INTO`; a substring check for `INSERT` against SQL that says `REPLACE`. Each of those passed a pin written the first way. The form that has held every time is a whitelist over what the code may do - no statement executed, no call made, nothing reached outside a permitted expression - because it does not depend on predicting how the next person writes the bad version. **A blacklist here is always one instance behind**, and the second patch to the same predicate is the signal to change shape rather than extend the list.

**An assertion that fails on a correct change is worse than no assertion**, because the cheapest way past it is deletion. A guard rejecting a properly-migrated column, and a flow count that breaks when a provider is deliberately removed, were both this - check a new seam assertion against the changes you already intend to make.

Crossed, and by what:

- **Closures that cannot be imported.** `CallbackHandler` lives inside `setup_google_auth`, so the only way to check it is to read the source. `TestTheCallbackPage` does, pinning three properties across its five tests: the page escapes what it shows, every `wfile` write goes through `_callback_page`, and the exception reaches the user only as `type(e).__name__` and is never reached unbound. It parametrises over every `setup_*` function it can discover rather than naming one, so a second flow added beside it inherits the pins instead of quietly having none.
- **The module import graph.** No behavioural test can see an unused import, and `doctor` importing `auth` or `api` would let a diagnostic rotate a token another host owns. `TestDoctorStaysOffline`.
- **Which code may print a path.** `test_no_logger_call_in_shared_code_carries_a_path` in `tests/test_seams.py`. Key on the logging *method*, not on the receiver's name - `logging.getLogger(__name__).info` is the same call as `logger.info` and a name match misses it.
- **Packaging consistency.** `test_the_declared_version_and_the_lockfile_agree`, same file.
- **A doc restating a list the code holds.** The README's scope table told readers to tick a scope `GOOGLE_SCOPES` had dropped, and nothing failed: a paired fact edited on one side only is this repo's most repeated defect. `test_the_readme_scope_table_is_the_scopes_that_are_requested` reads the table and compares it with the constant, and reads the paragraph beneath it separately - that one names the scopes this package declines, which is the opposite claim, so it must stay disjoint from what is requested. Either derive such a list or pin it this way; do not leave it to be noticed.
- **Which data type a fetch is given.** Every normaliser test mocks the client, so a path travels no further than the mock: replacing `"sleep"` with a type that does not exist leaves every behavioural test green while the real sync 404s and that table stops filling. `test_every_data_type_a_fetch_names_is_one_the_api_has` reads the literal each fetch is handed and checks it against `GOOGLE_TYPES`. The scope equality catches it too, but only where `_SCOPE_READERS` is not edited to match; this one fires either way.
- **Whether a tool a module defines ever reaches the wire.** Registration is a decorator that runs at import time, so a module `cli.py` does not name registers nothing: its tools are absent while the suite imports the module directly and every behavioural test on it passes. `test_every_tool_written_here_reaches_the_wire` asks the server's own registry, not the import list - a test that read `cli.py`'s imports would pass a tool registered by some other call and fail a correct change to how modules are discovered.
- **The lists a schema change has to move together.** A column added to `SCHEMA` reaches an existing database only if `_migrate` alters the table; miss that and `doctor` grades the database FAIL and tells a user with a long history to re-create it, for something an `ALTER` would have fixed. Adding a column with no migration passes every behavioural test. `TestTheMigrationLockstep` in `tests/test_seams.py` opens each file in `tests/schema_baselines/` and asserts the result matches `SCHEMA` exactly. `doctor._SELF_HEALING_COLUMNS` is *derived* from `db.MIGRATIONS` rather than restated, so it cannot be missed on its own; `test_self_healing_columns_is_exactly_what_migrate_adds` still earns its place by catching an entry whose `ALTER` adds nothing.
  - **Removing or renaming a column is not expressible.** `MIGRATIONS` is add-only, so a baseline database keeps the column forever while the lockstep asserts set equality - the only green route is deleting the baseline, which drops support for that release. Decide that deliberately rather than reaching for it under a red test.
  - **A baseline exists from 1.0.0 onwards, and `test_a_released_schema_is_always_on_file` is what keeps it that way.** With the directory empty every other test in the class iterates nothing and passes - which is what a package looks like before its first release, and it is when the hole is widest: a column added to `SCHEMA` then satisfies the whole suite, and the user who upgrades into it is told by `doctor` to re-create three years of rows. `db.MIGRATIONS` being empty is separate and is correct: nothing older than 1.0.0's schema exists yet. Data from elsewhere arrives through `importer`, which writes rows through this package's own writers rather than adopting another database's shape, so `MIGRATIONS` stays about our own history alone.
  - **Each baseline is `SCHEMA` as a release shipped it, named `X.Y.Z.sql`, and is written once.** It is added at *release* rather than when `SCHEMA` changes, so that every file describes a version somebody could be running rather than a state that only ever existed mid-branch. The procedure is in CONTRIBUTING's release steps; deleting one drops support for databases that old.
  - **Editing one is the escape hatch from a red lockstep, and only history can see it.** `test_no_older_baseline_has_been_refreshed_to_the_current_schema` exempts the newest file, which equals `SCHEMA` whenever nothing has changed since the last release - so with a single baseline on file, refreshing it to match a new column turns the whole class green. `test_no_baseline_has_been_changed_since_it_was_added` asks git **how many commits have touched each file**, not for a diff against HEAD: the maintainer commits the edit, after which the worktree and HEAD agree forever and a diff could never fire in CI. It says nothing about a baseline being added or deleted, which are the release step and the documented way of dropping support. It skips without git, without a checkout, on a shallow clone (one commit per file whatever the history), and while no baseline is committed.
  - **One baseline is not enough, and the gap is invisible.** A table the baseline predates is created whole by `CREATE TABLE IF NOT EXISTS`, so a column added to *that* table satisfies a single-baseline check while still breaking the database of a user who has the table and not the column - and the same check then rejects the correct migration, pointing a maintainer at exactly the wrong repair. Covering every released vintage is what makes a green run mean what it says.
- **Two more lists that restate `SCHEMA`'s tables.** A table absent from `_UPSERT_KEYS` raises inside `_upsert`, which on the sync path `run_sync`'s catch-all records as an exception type, leaving `doctor` reporting a clean log; one absent from `_DATA_TABLE_MAP` is quieter still, re-fetching its whole window every run with nothing looking wrong. `test_every_table_is_accounted_for_by_the_lists_that_enumerate_them` names the excluded tables rather than inferring them.
- **That every `save_*` actually writes through `_upsert`.** Only five of the twelve upserted tables have a preservation test, so a helper reverted to its own `INSERT OR REPLACE` keeps its `_UPSERT_KEYS` entry and passes the whole suite while the entry means nothing. `test_no_save_helper_reaches_the_database_except_through_the_upsert` reads the source and pins both directions, `save_core_temperature` being the one helper that must not upsert.
- **Whether the harness lets a test reach the network, or see this machine's credentials.** Deleting `_no_network` fails its pin anywhere. Deleting `_no_real_credentials` fails nothing wherever no credential exists, which is what CI is; on a machine holding one it fails its own pin and takes fourteen tool tests with it. `test_the_suite_cannot_reach_the_network` pins the first and `test_the_suite_cannot_see_real_credentials` the second - one test does not cover both. See "Running tests" for why the refusal is `pytest.fail` and why `helpers` is patched as well as `config`.
- **Whether an exception's message survives the trip to the model.** The conversion happens in `require_auth`, a layer above the one every tool test calls, so a class that forgets the `GoogleHealthError` base raises fine, is caught fine, and passes everything behavioural while reaching the client as a bare `Error executing tool <name>`. `test_every_exception_this_package_defines_reaches_the_model` walks the package's own classes and asks the hierarchy rather than reading the `class` statement, and names its exclusions in `_NOT_MODEL_FACING` so leaving the base off has to be a decision. Three things about how it walks are load-bearing. Two are pinned, each measured by removing it and watching a bad class go unreported: it keys each class by its module and name, or a conforming class shadows a broken one of the same name in another module; and it seeds itself with the package module, since `walk_packages` yields what is *inside* the directory and never `__init__.py`. The third, `onerror`, has no mutant that distinguishes it from its own deletion while `tools` is the only subpackage, because the test imports that one directly before the walk would recurse into it; it guards a nested subpackage the layout does not have yet, so do not read it as pinned. **It sees classes this package defines, not raise sites**: a bare `RuntimeError` or `ValueError` raised here is masked and nothing reports it, which is why `refresh_before_query` raises `LiveRefreshFailed` rather than a bare `RuntimeError`.
- **Which modules hold a credential path of their own.** `_no_real_credentials` patches a fixed pair of modules, and a new one importing these names by value escapes it in silence - which is how `helpers` kept the real paths while every other signal said the suite was isolated. Nothing on CI can see it: with no credential present there is nothing to observe either way. `test_only_the_expected_modules_hold_a_config_path`.

Crossed only from outside this repo, which an outside contributor will not have:

- **The mock boundary.** Tool and normaliser tests patch the client's own functions, so the mock sits above the real client and the shape it hands back is agreed between two mocks rather than measured. Partially crossed by `TestTheArrayEndpointsSurviveTheRealClient`, which drives `devices` and one Google normaliser from the response body up - the pattern to copy when a change touches that layer.
- **The wire contract.** The suite calls tool functions directly and never the server, so a tool's description and its input schema are untested: replacing a docstring with nonsense, or changing a parameter's type annotation, passes the whole suite. A rename is caught, but only incidentally - `tests/test_tools.py` imports the functions by name - so do not read that as contract coverage. Dump the tool list and schemas from a real server and diff them across the change.
- **The pre-commit guard.** `scripts/check-no-data.sh` is not exercised by pytest at all. Stage a probe file per class and check reject against expectation.

## Database schema

SQLite at `~/.local/share/google-health-mcp/google_health.db` (gitignored). The exact column definitions live in `SCHEMA` in `src/google_health_mcp/db.py` (the source of truth); the list below is a navigational overview that also notes the non-obvious semantics.

- `heart_rate` - date, resting_hr, zones (JSON)
- `activity` - date, steps, calories_out, active_minutes, very/fairly/lightly active, sedentary, floors, distance_km. **The five minute columns have no source in this API and arrive only by import**, so on an install with no imported history they stay NULL - and `health_trends activity` reports `avg_active_minutes` from one of them, which is `null` in every period until something fills it. Reasoning for not deriving them: `sync_activity`'s docstring
- `exercises` - log_id, date, name, duration_min, calories, avg_hr, steps, distance_km, start_time, source, log_type
- `sleep` - date, total_minutes, efficiency, start/end_time, deep/light/rem/wake_minutes, sessions (one row per night; a fragmented night's sessions are summed, `sessions` > 1 flags the split), sleep_period_minutes
- `weight` - date, weight_kg, bmi, fat_pct
- `spo2` - date, avg, min, max, avg_ci_low, avg_ci_high
- `hrv` - date, daily_rmssd, deep_rmssd
- `azm` - date, total_minutes, fat_burn_minutes, cardio_minutes, peak_minutes
- `breathing_rate` - date, breaths_per_min
- `skin_temperature` - date, nightly_relative (degrees C from baseline), log_type, nightly_absolute, baseline
- `core_temperature` - datetime (YYYY-MM-DDThh:mm:ss), date, temp_celsius; PRIMARY KEY (datetime, temp_celsius) - manually-logged body temp keyed by timestamp+value so multiple (even same-second) readings per day are preserved while exact repeats de-dup. **Its `provider` is currently unwritable and stays NULL**: `save_core_temperature` is `INSERT OR IGNORE` over three named columns and the table is deliberately outside `_UPSERT_KEYS`, so a writer that wants to set it must name it. The seam test skips this helper by name and will not notice
- `cardio_fitness` - date, vo2_max_low, vo2_max_high (a reported range), vo2_max (a single value)
- `food_log` - date, calories_in, water_ml
- `ecg` - reading_id, date, start_time, avg_bpm, classification, lead_number, sampling_hz, scaling_factor, duration_sec, waveform, device_model. `classification` is stored as the enum given (`NORMAL_SINUS_RHYTHM`, `ATRIAL_FIBRILLATION`, four inconclusive variants, unspecified, not-analyzed) rather than collapsed to a boolean. `waveform` is the sample array as JSON text and `duration_sec` is stored rather than derived on read, because the interval carries only a start time - a reading's length is samples over frequency, and without a frequency there is no duration
- `irn` - alert_id, date, start_time, end_time, alert_windows (JSON text), device_model
- `sync_log` - sync history (used by auto-sync to decide when to re-fetch)

**`provider` is on every table above except `sync_log`**, whose `data_type` and timestamp already carry that. It names **the provider of the most recent write, not of the row** - an upsert keeps columns the new writer did not name, so a row can hold one provider's efficiency beside another's stage minutes and `provider` says only who wrote last. NULL means no writer has set it, which in practice is a row that arrived by import - `importer` deliberately never names it, and that is what marks a row as imported. **Every sync writer must name it on every write**, or a row it corrects keeps the previous writer's name. Do not "fix" the importer to set it: `_days_another_provider_recorded` identifies imported workouts by `provider IS NULL`, so filling it would silently disable the exercise de-duplication.

**Four columns exist because the same quantity is defined differently by different providers, and merging them would corrupt a series rather than break it.** Never widen one to hold both.

- `spo2.avg_ci_low`/`avg_ci_high` are a **confidence interval on the average** (`lowerBoundPercentage`/`upperBoundPercentage`), not observed extremes. `min`/`max` are the observed nightly extremes. Averaging the two definitions in one trend reports a step change that reads as physiological.
- `cardio_fitness.vo2_max` is a **single value**; `vo2_max_low`/`vo2_max_high` are a reported range. Writing one value into both ends collapses a real band to a point.
- `skin_temperature.nightly_absolute` and `baseline` are absolute degrees C. `nightly_relative` is their difference, which is the quantity the column holds, so a Google reading is stored by subtraction rather than in a column of its own.
- `sleep.sleep_period_minutes` is **not** time in bed. It is `minutesInSleepPeriod`, the delta between bedtime and wake time. It makes a *stated* efficiency computable; do not use it to reconstruct `efficiency`, which has no source in this API and stays NULL rather than being approximated.

**The read side carries both definitions rather than choosing one.** `_trend_spo2` and `_trend_cardio_fitness` report each series beside the other with the count of readings behind it (`nights_observed_extremes` / `nights_confidence_interval`, `readings_range` / `readings_single_value`), so a period spanning the switchover says which rows it holds instead of averaging two quantities or ending silently. The period keys are named for what they are - `avg_nightly_ci_low` is the mean of the nightly bounds, not a confidence interval on the period's average. Pinned by `TestTheTwoSpo2Definitions` and `TestTheTwoCardioFitnessDefinitions` in `tests/test_analysis.py`. Compare mode reports the definition-neutral average for SpO2 and both VO2 max definitions for cardio fitness; a summary that reads only one definition is the same defect one surface along.

**`_TREND_FNS` and `_COMPARE_QUERY_FNS` must hold the same types**, since one error message offers both - drop an entry from either and a type is refused in the same sentence that recommends it. Neither is derived from `CACHED_DATA_TYPES`, deliberately: `ecg` and `irn` are episodes rather than daily series and have no trend at all. Pinned by `test_the_two_dispatches_offer_the_same_types`.

## Running tests

Run the suite as [CONTRIBUTING.md](CONTRIBUTING.md) describes - all of it uses temporary SQLite and fictional data. What that file does not cover:

**No test sees the machine's own credentials, and that is what makes the suite mean the same thing everywhere.** `_no_real_credentials` in `tests/conftest.py` points `GOOGLE_TOKENS_PATH` and `GOOGLE_CLIENT_PATH` at an empty directory for every test. It is a data-safety mechanism, not tidiness: every query tool opens with `refresh_before_query` (and `health_trends` with `auto_sync_if_stale` directly), which syncs whenever the cache holds no `sync_log` row for the type, and a temp database never has one. Given a usable token that sync succeeded, writing the real account into the test's database and into the windows the test asserts over; with none it failed and was swallowed by design. The same suite passed on CI and failed on a machine holding credentials, for a reason neither result named. **Both `config` and `helpers` are patched, and the second is the one to keep**: `helpers` imports the two paths by value, so it holds its own copies, and a fixture patching `config` alone leaves `require_auth` - worn by every tool - reading the real files while everything else looks isolated. `auth` and `doctor` reach them through `config` at call time. Pinned by `test_the_suite_cannot_see_real_credentials` in `tests/test_seams.py`, whose equality half fires anywhere and whose existence half fires only where a credential is present.

**`_no_network` is the backstop, and `pytest.fail` rather than `assert` is load-bearing.** It replaces `urllib.request.urlopen`, which is measured to be the only call this package makes a request through (`api.py`, `auth.py`) and is not pinned as such - a route opened through `socket`, `http.client`, a subprocess or a new dependency would pass it. `refresh_google_token` and `auto_sync_if_stale` both end in `except Exception`, so an `AssertionError` raised in that fixture is caught by the code under test and reported as an ordinary network failure, which is the silence the fixture exists to break; `Failed` derives from `BaseException` and neither catch-all can absorb it. Pinned by `test_the_suite_cannot_reach_the_network` in `tests/test_seams.py`, which asserts the type as well as the message. A test that means to exercise a request patches `urlopen` itself, which replaces the fixture for its duration.

**Neither fixture isolates the database, and one call resolves it implicitly.** `auto_sync_if_stale` calls `db.get_db()` with no argument, so it opens `db.DB_PATH` - the real cache unless the test patched it. `get_db` creates the file and the whole schema before any request is made, and a refused sync still writes one `auth_error` row through `run_sync`'s auth branch, so the refusal above is not what keeps the real cache clean: **the per-test `db.DB_PATH` patch is the only thing that does**, and it is convention rather than construction. A tool test added without it is the way this comes back. Note `GOOGLE_HEALTH_MCP_DB_PATH` does work from outside, but only exported before pytest starts - `config` resolves it at import, so `_isolate_from_ambient_env`'s `delenv` cannot move a path that is already bound.

**Do not isolate by setting `GOOGLE_HEALTH_MCP_CONFIG_DIR` to an empty directory**: `test_default_paths_exist` asserts the *default* config directory is named `google-health-mcp`, and the override makes it the temp directory's name instead, so that test fails for a reason that has nothing to do with the change under test.
